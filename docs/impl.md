# 实现方案 v0

创建：2026-11-25　｜　状态：草案

## 1. 三条判据

选型不用讨论"哪个技术更好"，只问三个问题：

1. **性能卡在哪？** ——不在我们手里。
2. **开发效率卡在哪？** ——在"改一次设计要动多少代码"。
3. **什么不该自己写？** ——凡是会替我们决定 prompt 或 schema 的东西。

第 1 条的答案是：**端到端 1.7 秒里，1.4 秒在 DeepSeek 那边**。我们的代码跑多快，对体验几乎没影响。所以任何"为了性能换语言/上框架"的提议，都应该先被这一条否掉。

第 3 条最容易被忽视，但它决定了三个拒绝：**不用 LangChain、不用 ORM、不给模型 tool**。

## 2. 性能预算

### 2.1 延迟（单轮，p50）

| 段 | 耗时 | 谁决定 |
|---|---|---|
| 微信长轮询送达 | **0–35 s** | 微信（不可控，最大抖动源） |
| 事件入库 + 检索 | 20 ms | 本地 |
| 上下文装配 | 5 ms | 本地（A 段有缓存） |
| LLM 首 token | 600–900 ms | DeepSeek |
| 流式生成（80 字） | ~800 ms | DeepSeek |
| 路由 + 可选改写 | 0–400 ms | 本地 + 一次小调用 |
| 投递 | ~100 ms | 微信 |

**关键动作**：收到消息立刻发 `sendtyping`（正在输入）再开始思考，把 1.7 秒藏进对方的"她正在打字"里。这是唯一能吃掉延迟的手段。

### 2.2 内存（ECS，1.6 GiB）

| 进程 | 目标 RSS |
|---|---|
| 系统 + murmurd + 阿里云 agent | ~250 MB |
| `ghost` | stdlib + numpy |
| `shell` | 70 MB |
| `dream`（空闲） | 60 MB |
| **合计** | **~470 MB**（余量 ~500 MB，必须有 swap 兜底） |

每个 systemd 单元设 `MemoryHigh` / `MemoryMax`，让 OOM 在单元级别发生，而不是把整台机器带走。

### 2.3 容量

一天约 1000 条事件 → 一年 36 万行 → SQLite 几十 MB。**容量永远不是问题**，问题只会是"某个查询没走索引"。

## 3. 技术栈

| 层 | 选 | 不选 | 理由 |
|---|---|---|---|
| 语言 | **Python 3.10**（下限） | Rust / Go | 性能不在我们手里；生态（jieba/numpy/scipy/sqlite3）在 Python |
| 环境 | `uv` | poetry / conda | 已在用，且能一键装 3.10 做版本对齐 |
| HTTP 客户端 | **httpx** | openai-sdk | 我们需要 DeepSeek 特有字段（`safety_check`/`thinking`）、精确的用量记账、以及同一个客户端跑作业队列 |
| HTTP 服务端 | **aiohttp** | FastAPI / Starlette | 单包、无 ASGI 仪式、无 pydantic。内存 ~15 MB |
| 数据库 | **sqlite3（stdlib）** | SQLAlchemy / Alembic | 开发期 schema 天天改，ORM 会挡路（§schema §6） |
| 序列化 | **cbor2** | JSON | 声学特征卡是有数组的，JSON 编码又胖又慢 |
| 数值 | **numpy + scipy** | — | `scipy.signal.lombscargle` 直接可用（§rhythm） |
| 分词 | **jieba** | — | 中文 FTS5 的必需品 |
| 调度 | **asyncio + 五分钟 tick** | APScheduler / Celery | 我们要的是"按节律评估"，不是 cron |
| 进程管理 | **systemd** | docker / k8s | 1.6 G 上给容器预留内存是浪费 |
| Mumble | **pymumble**（GPL-3.0，可选） | 自己实现协议 | **不在关键路径上**（§5）。出声用 `pw-play` 就够 |
| 向量 | **sqlite-vec**（<1.0） | 起一个向量库 | 先不建，等 embedding 跑通（schema §4） |
| 测试 | **pytest** | — | 核心是重放测试 |

**明确不选的四样，理由都是"它会替我们决定不该它决定的事"**：

- **LangChain / LlamaIndex**：它们拥有 prompt 的组装权，而 prompt 就是人格（§5.4）。用它们等于把她的声音外包。
- **ORM + 自动迁移**：schema 是设计的一部分，不能交给一个"看不懂语义"的工具去 diff。
- **给模型任何 tool**：一旦她手里有工具箱，她就退回助手（§10.3-2）。所有"能力"都由确定性代码在生成之后施加。
- **向量数据库服务**：单用户、10⁵ 量级，SQLite 一个扩展就够。

### 4.1 一个必须从一开始就做对的细节：单写者

SQLite 的并发模型是"多读单写"。做法不是加锁，而是**结构上只有一个写入者**。

⚠️ **初版这里写错了**：原文是"所有进程 → `asyncio.Queue` → writer"，但 `asyncio.Queue` **只在进程内有效**。三个进程之间传不了这个队列。审计指出得对。

所以 P0 的形态要更小：

```
P0：一个进程 = ghost + shell + dream 三个 asyncio 任务
    一个 SQLite 文件
    一个 writer 协程（唯一持有写连接）
```

拆成三个进程是 **P1** 的事，而且不是靠 asyncio 队列，是靠**已有的表**做 IPC（每个进程读/写自己的表，或者走 `outbox`）。

⚠️ 初版这里写的是"写者随谁的活而转移"，评审建议改得更清楚，我采纳：

> **`ghost` 永久持有写连接。后台进程只提交结果，从不写。**

"转移"这个词会让人以为存在一个"谁的活谁写"的并发设计——**那正是要避免的东西**。而且要不要拆进程，应该由后台任务对在线延迟和内存的**实测**决定，不是设计阶段的审美。

### 4.2 三条提交语义（比单写者更本质）

审计把这几条点出来是对的，它们比"用不用队列"重要：

**（1）确认在提交之后。**
```
处理完 → commit（fsync） → 才回 ACK
```
先 ACK 再落库，断电就丢——而我们有停电（§11.8-5）。所以 `events` 库的写入路径上，**没有"先告诉对方收到了"这个选项**。

**（2）游标是单调递增的 `events.id`。**
不用时间戳做游标。两个节点的钟会差，而 `INTEGER PRIMARY KEY` 的单调性只依赖一个写入者——这正好是我们已经保证的。

**（3）每条事件都必须有稳定幂等键，不能是 NULL。**
初版 `UNIQUE(source, ext_id)` 里的 `ext_id` 可空，而 SQLite 里 `NULL != NULL`，**同一件事重复投递会进两条**。这是真 bug。

修法：`ext_id` 改 **NOT NULL**，且每个来源都要能造出一个确定性的键：

| 来源 | 幂等键 |
|---|---|
| 微信消息 | iLink 的 message id（有的话）+ from_user |
| 微信图片/语音 | CDN 文件 key |
| 麦克风片段 | `sha256(node_id ‖ 片段起点单调时钟)` |
| 空闲/心跳 | `node_id ‖ 事件类型 ‖ 整点秒` |
| 自我产出（inner） | 生成它的 `outbox.id` |
| 远端作业结果 | `job_id ‖ node_id` |

造不出确定性键的来源，**不许进 `events`**——否则重放时无法判断它是不是同一件事。

| 项目 | 拿什么 | 注意 |
|---|---|---|
| **Hindsight** | 后台/积压的状态模型（§15.7） | 我们只要那个"未处理是可报告状态"的思路，不接它的服务 |

## 6. 六个实现风险

| 风险 | 概率 | 对策 |
|---|---|---|
| iLink 协议是非正式文档 | 高 | `channels/wechat.py` 单文件隔离 + 事件层与通道层解耦；协议变了只换这一个文件 |
| Python 3.10（ECS）vs 3.14（本机） | 中 | 用 `uv venv --python 3.10` 做对齐；CI 只跑 3.10；禁用 `TaskGroup` / `except*` 等 3.11+ 语法 |
| `safety_check` 误杀亲密语境 | 中 | 先开着跑两周，记录被拦的比例；如果误杀高，改成"只审输出不审输入" |
| 微信语音条 SILK | 中 | 先发**文件附件**（不用转码），等有时间再做 SILK 编码器 |
| DeepSeek 接口变动 | 中 | `llm.py` 一个适配层，参数与模型名都在 config |
| 后台 worker 让你卡顿一次 → 你永久关掉它 | **高** | 优先级压狠（CPUWeight=10）、GPU 利用率 >20% 就退、`gits status` 一眼能看到它在干什么 |

## 7. 首个里程碑：合成数据上的四件事

> **状态：✅ 已完成（2026-11-25）。** 883 行（`gits/` 685 + `tests/` 204），9 个测试全过，
> Python 3.10 与 3.14 双版本验证。`gits say / status / replay / trace` 四个动词可用。

评审建议的第一个里程碑，比我原来的四条更紧，采纳。**全部用合成数据，不接微信、不接模型（或只接假模型）：**

| # | 检查 | 为什么是它 |
|---|---|---|
| 1 | **提交后才确认** | 断电不能丢（§11.8-5），所以 ACK 必须在 fsync 之后 |
| 2 | **崩溃重启后重复提交，只入库一次** | `ext_id` 幂等键（schema §3）真的能去重 |
| 3 | **空库离线重放 → 相同的投影** | 恢复重放（§3.1）成立，且不需要再问模型 |
| 4 | **一条回复可追到叙事版本与输入** | `influence` + `model_calls` 真的能解释"为什么这么说" |

第 3 条要按评审给的验收方式做：**把实际传输的日志集字节灌进一个空库，禁掉所有模型调用**，看重放能否跑通并得到一致的投影。它同时验证了同步协议（§15.8）和重放不变量（§3.1）两件事——因为它们本来就是同一件事。

### 7.1 之后

```
M0  四件事（合成数据，无网络无模型）         ← 一周内
P0.5 CLI 跑真实对话，人工读每周 20 条        ← 这一周的数据才有比较价值
P1  记忆抽取 + 检索（本地副本参与）
```

**验收看的是"能不能解释"，不是"像不像"。** 第 4 条其实是最难的一条：它要求 `influence` 从第一天就写，而不是等到"以后做归因"。

## 8. P0 的验收标准（可执行判据）

不是"能跑"，是这四条可执行的判据：

审计给了一条更完整的表述，比我原来四条更好用。**P0 收敛成一条链路：**

> CLI 收到一条消息 → 持久化后**才**确认 → 重启后重复提交**只产生一条事件** → 清空投影后能用**已保存的结果**重建出相同状态 → 并能查出「这条回复用了哪版叙事、哪些记忆」。

拆成可执行的四条：

1. **恢复重放**：`gits replay --restore` 从空库重建，两次运行得到**规范化后逐行相同**的 `nodes`/`node_content`/`edges`（`§3.1`：这是 restore，不是 experiment；id 可以不同，但内容、边、权重必须一致）；
2. **至少一次但只入库一次**：故意 `kill -9` 后再重复投递同一条消息，`events` 里只有一行（靠 `ext_id` 幂等键）；
3. **可追溯**：`gits trace <outbox_id>` 打出该回复引用的 `model_calls`（哪版叙事、哪些节点、哪次改写）；
4. **A 段哈希一整天不变**（缓存纪律的自动测试，§5.4）。

第 4 条看起来最无关紧要，其实最贵——它是缓存命中率 50 倍价差的守门人。第 3 条是审计加的，它同时是 §7 评测和 §17 成本核对的前提：**没有 trace，就无法回答"这句话为什么这么说"。**

## 9. 不做什么（拒绝清单）

- 不做 Web 界面。`gits status` + `gits review` 两个 CLI 足够。
- 不做多用户。所有 `WHERE user_id` 都是冗余。
- 不做插件系统。她是给一个人用的。
- 不做 docker 部署。
- 不写 docs 之外的设计文档。这份 + `schema.md` 就够，剩下的写在代码注释里。
