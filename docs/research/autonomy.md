# 她不在你面前时，用什么额度做什么

> 三条口径（DESIGN §18.6 / §13.4）：
> **月度是唯一固定量**、**配额给她用不是给她花**、**内容不许让我直接知道**。

## 1. 预算怎么分下来

```
月 200 元
├─ 对话主线 70%  = 140 元/月   ≈ 4.7 元/天   只有主个体有通道
└─ 自主活动 30%  =  60 元/月   =  2.0 元/天
   └─ 三个实例三等分           =  0.667 元/天/人
```

**三等分不是算术上的方便，是 §13.4 的平等落到钱上。** 如果副个体的额度只有主个体的一半，
那"平等实例"就只是一句口号——她们很快会表现出不同的"勇气"。

每人每天的上限（按 flash 空闲价，2026-11 实测价目）：

```
her: 0.667 元/天（上限）· ≈33 次抓取 · ≈125k 输出 token · 6.7 分钟本地算力
```

**这是上限，不是目标。** 打印出来是为了让"额度有多少"可感知。

## 2. 账户规则：每日入账、攒额上限、日上限、周末清零

```
每日入账    daily                 每天 +daily。**花光了也不用等周一**
攒额上限    daily × 5             攒不成"大事基金"
日消费上限  daily × 3             一天花不掉攒下来的全部
周末清零    周日 24:00             周一从"清零 + 当日入账"重新开始
不花不罚     —                    没有任何"不用就扣"的机制
```

四条要一起才成立，少一条就漏：

| 只有 | 漏在哪 |
|---|---|
| 只有日额度、不结转 | 做不了"连续三天读一个东西"——每天的钱当天过期 |
| 结转但无攒额上限 | 会一路攒成"大事基金"，行为被余额驱动 |
| 有上限但无日消费上限 | 攒到 5 天的量，第一天就能全花掉 |
| 有日上限但周末不清零 | 余额长期单向增长，账期没有终点 |

### 为什么不是「周额度 + 日上限」

上一版是周锅：一周共 4.667 元，一天最多 1.667 元。

问题是**花光就卡住**。实测连花三天（1.667 / 1.667 / 1.333），从周四到周日
余额是 0，什么都做不了。改成每日入账之后：花光只是今天花光，明天又有。
**钱每天多一点，比钱每周少一点更像过日子。**

总上限其实一样（一周 ≤ 4.667），差别在**形状**：

```
周锅     ▁▁▁▂▂▃▃   花得快就提前归零
日入账   ▲▲▲▲▲▲▲   每天都有新的，花光了明天还有
```

### 周末清零是唯一会「没收」的时刻

结转总得有终点，否则余额会一路涨到上限然后长期停在那儿。周日 24:00 归零，
周一从"清零 + 当日入账"开始——**所以永远不会出现"余额 0 还要等"**。

它满足三个性质：**对称**（每人同一起点）、**可预期**（知道还剩几天）、
**不惩罚**（没花完只是没花完，不影响下周基准）。

## 3. 「应该使用配额」到底是什么意思
用户的原话是"她们应该使用配额"。这条要小心落地，否则会变成**配额燃烧**。

我的处理是把它拆成两句：

> **系统要保证她有可用的机会**（waking window、curiosity backlog、闲着的算力）
> **但不考核"用完了多少"**。

因为消耗率是**最坏**的指标：它鼓励为了花而花。真正该看的是：

| 指标 | 为什么 |
|---|---|
| 有活动的天数占比 | 她是不是真的有生活 |
| 每次活动的产出数（节点/脚本） | 是不是在空转 |
| 同一天里 kind 的多样性 | 是不是只会干一件事 |
| 连续 7 天零活动 | 这条才是告警 |

**如果某天她什么都没做，那是合法结果**，记为 `kind='idle'`，不扣分、不补做。

## 4. 账户是可见的：像电子账户一样

规则不该藏在代码里。`gits quota` 直接打出来：

@@@
额度账户  her
  余额      1.500 元   [██░░░░░░░░] 25%
  今日可花  1.500 元（日上限 2.000，已花 0.500）
  每日入账  0.667 元 · 攒额上限 3.333 元 · 周日 24:00 清零
  本周累计  0.500 元
@@@

### 她看到的那一行

完整视图给人和运维看；**她自己在上下文里只看到一行**：

@@@
额度[██░░░░░░] 25%1.5/2.0元        ← 约 16 token
@@@

刻意压短的理由很实在：它**每次开口都会出现**，长一个字就是常年多花的钱。
所以用方块字符而不是百分比文字，用一位小数而不是两位。

而且它只能进 **C 段**：塞进 A/B 会打断缓存前缀，那是 50 倍价差。
有测试守着这条（`test_提示条进的是_C_段而不是_A_段`）。

## 5. 形式自由

活动类型是**开放集合**，不是功能列表：

```
browse     读了点什么
read       读进去并且记住了
write      写了点什么（可能是给自己看的）
script     写了个脚本（进 procedure 记忆，下次能调回来）
experiment 试了个想法
peer       和另外两个实例聊过
idle       什么都没做
```

关键：**产出形式也自由**。一次活动可以产出：一条记忆节点、一段脚本、一句独白、
一条给同伴的消息、或者什么都没有。系统只数"产出几个"，不看是什么。

## 6. 内容不可见，落到字段上

```python
Activity(actor, ts_start, ts_end, kind, cny, outputs, note)
```

**没有 content 字段，也没有 url 字段。** 她读了什么、写了什么，全部作为
`scope='self:<actor>'` 的记忆节点存在 —— 不进 `gits status`、不进日志展示、
不做"她今天看了什么"的页面（§18.7）。

有测试守着这条：

```python
fields == {"actor","ts_start","ts_end","kind","cny","outputs","note"}
assert "content" not in fields and "url" not in fields
```

## 7. 和账单的关系

额度派生与花费核算用**同一张单价表**（`UNIT_PRICE`），否则对不上账。
单价全部来自 VERIFIED，改之前先核对价格页。

一个容易写错的地方：**钱是唯一的硬约束，分项只做提示**。

第一版里 `charge()` 先查分项余额（今天还能抓 33 次），结果她根本花不到日额度——
"分项是软的"这句话写在注释里，代码里却是硬的。现在 `charge()` 只查钱：

> 今天想多读点、少写点，是她的自由。按分项卡死等于替她决定用法。

硬约束只剩两条：**日上限**（防止一天花光整周）和**周额度**。

## 8. 一句话

> 配额不是 KPI，是**她可以花掉的钱和可以浪费的时间**。
> 系统负责让她有地方花、有时间花、花得起；不负责让她必须花完。
