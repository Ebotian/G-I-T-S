# 她不在你面前时，用什么额度做什么

> 三条口径（DESIGN §18.6 / §13.4）：
> **月度是唯一固定量**、**配额给她用不是给她花**、**内容不许让我直接知道**。

## 1. 预算怎么分下来

```
月 200 元
├─ 对话主线 70%  = 140 元/月   ≈ 4.7 元/天   只有主个体有通道
└─ 自主活动 30%  =  60 元/月   =  2.0 元/天
   └─ 三个实例三等分           =  0.667 元/天/人
```

**三等分不是算术上的方便，是 §13.4 的平等落到钱上。** 如果副个体的额度只有主个体的一半，
那"平等实例"就只是一句口号——她们很快会表现出不同的"勇气"。

每人每天的上限（按 flash 空闲价，2026-11 实测价目）：

```
her: 0.667 元/天（上限）· ≈33 次抓取 · ≈125k 输出 token · 6.7 分钟本地算力
```

**这是上限，不是目标。** 打印出来是为了让"额度有多少"可感知。

## 2. 周清、日结转、日上限

```
周额度   = 日额度 × 7
今天能花 = min(日上限, 周额度 − 本周此前已花)
日上限   = 日额度 × 2.5
周一清零
```

三条要一起才成立，少一条就漏：

| 只有 | 漏在哪 |
|---|---|
| 只有日额度 | 做不了"连续三天读一个东西"这种项目——每天的钱当天过期 |
| 只有周额度 | 一周的钱第一天就能花光，**等于没有日额度** |
| 周额度 + 结转、没有日上限 | 同上，结转把上限磨平了 |
| **周额度 + 日上限** | 结转是**算出来的**，不用搬余额 |

### 为什么用「周锅」而不是「搬余额」

第一版写的是"今天的余额搬到明天"。第一天花掉 2.5（日上限），
但那天只"挣"了 0.667，余额变成 **−1.833**。

负余额只有两种处理，都不对：

- 忽略它 → 等于可以**透支整周**；
- 记成欠账 → 等于**惩罚**她今天多花。

改成周锅一算就干净：能花的永远不超过本周剩下的，负数根本不会出现。

### 为什么周一是唯一会「没收」的时刻

结转总得有个终点，否则会一路攒成"大事基金"——那时她的行为被余额驱动，
而不是被兴趣驱动。周一切零：

- **对称**：每个人每周一从同一个起点开始；
- **可预期**：她知道自己还剩几天可以攒；
- **不惩罚**：没花完只是没花完，不影响下周的基准额度。

### 不花不罚

没花完的只是留在周锅里。一周真的一分没花，下周一的起点和上周一模一样。

实测（每天想把当日上限花光）：

```
第1天 上限 1.667 花 1.667
第2天 上限 1.667 花 1.667
第3天 上限 1.333 花 1.333     ← 周锅只剩这么多
第4天 上限 0.000               ← 花完了，等到周一
一周共花 4.667（周额度 4.667）
```

## 3. 「应该使用配额」到底是什么意思

用户的原话是"她们应该使用配额"。这条要小心落地，否则会变成**配额燃烧**。

我的处理是把它拆成两句：

> **系统要保证她有可用的机会**（waking window、curiosity backlog、闲着的算力）
> **但不考核"用完了多少"**。

因为消耗率是**最坏**的指标：它鼓励为了花而花。真正该看的是：

| 指标 | 为什么 |
|---|---|
| 有活动的天数占比 | 她是不是真的有生活 |
| 每次活动的产出数（节点/脚本） | 是不是在空转 |
| 同一天里 kind 的多样性 | 是不是只会干一件事 |
| 连续 7 天零活动 | 这条才是告警 |

**如果某天她什么都没做，那是合法结果**，记为 `kind='idle'`，不扣分、不补做。

## 4. 形式自由

活动类型是**开放集合**，不是功能列表：

```
browse     读了点什么
read       读进去并且记住了
write      写了点什么（可能是给自己看的）
script     写了个脚本（进 procedure 记忆，下次能调回来）
experiment 试了个想法
peer       和另外两个实例聊过
idle       什么都没做
```

关键：**产出形式也自由**。一次活动可以产出：一条记忆节点、一段脚本、一句独白、
一条给同伴的消息、或者什么都没有。系统只数"产出几个"，不看是什么。

## 5. 内容不可见，落到字段上

```python
Activity(actor, ts_start, ts_end, kind, cny, outputs, note)
```

**没有 content 字段，也没有 url 字段。** 她读了什么、写了什么，全部作为
`scope='self:<actor>'` 的记忆节点存在 —— 不进 `gits status`、不进日志展示、
不做"她今天看了什么"的页面（§18.7）。

有测试守着这条：

```python
fields == {"actor","ts_start","ts_end","kind","cny","outputs","note"}
assert "content" not in fields and "url" not in fields
```

## 6. 和账单的关系

额度派生与花费核算用**同一张单价表**（`UNIT_PRICE`），否则对不上账。
单价全部来自 VERIFIED，改之前先核对价格页。

一个容易写错的地方：**钱是唯一的硬约束，分项只做提示**。

第一版里 `charge()` 先查分项余额（今天还能抓 33 次），结果她根本花不到日额度——
"分项是软的"这句话写在注释里，代码里却是硬的。现在 `charge()` 只查钱：

> 今天想多读点、少写点，是她的自由。按分项卡死等于替她决定用法。

硬约束只剩两条：**日上限**（防止一天花光整周）和**周额度**。

## 7. 一句话

> 配额不是 KPI，是**她可以花掉的钱和可以浪费的时间**。
> 系统负责让她有地方花、有时间花、花得起；不负责让她必须花完。
