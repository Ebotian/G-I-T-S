# 上下文预算与整理（cache-aware）

> 起因：你说「参考 DeepSeek 的缓存时间，超时后长上下文会重新计费，此时应该整理再开新的；
> 连续上下文超过 60% 开始整理，80% 强制，如果离上次对话很近要告知；60% 触发闲时整理，
> 当预计空闲时间大于预计整理时间就开始」。
>
> 我查了官方文档、也拿到了实测数据。结论是**方向对，但两个参数要换**：
> 「缓存时间」不可读，得靠推断；「60%/80% of 最大值」永远不触发（1M 的 60% 是 60 万 token）。

## 1. 官方文档说清的三件事

来源：`api-docs.deepseek.com/zh-cn/guides/kv_cache`（2026-11-25 抓取原文）

**① 命中要求「完整匹配缓存前缀单元」，不是「前缀相似」。**

> 每条缓存前缀是一个独立的完整单元。后续请求只有在**完整匹配**缓存前缀单元时，才能命中缓存。

**② 每次请求会落两个单元**：用户输入结束位置、模型输出结束位置。
另外还会做「公共前缀检测落盘」和「按固定 token 间隔落盘」。

**③ TTL 是「几个小时到几天」，且不可控、尽力而为。**

> 缓存构建耗时为秒级。缓存不再使用后会自动被清空，时间一般为几个小时到几天。
> 缓存系统是「尽力而为」，不保证 100% 缓存命中。

→ **所以「超过缓存时间就整理」这条规则本身是对的，但触发条件不能是读一个 TTL 数字**
（没有这个数字，也没有这个接口）。只能用 `usage.prompt_cache_hit_tokens` **推断**。

## 2. 我们实测到的：命中率 0

三次连续调用，`prompt_cache_hit_tokens` 全是 0。当时以为是「前缀太短」。
读完文档才明白真正原因——**是我们自己的 prompt 形状在杀缓存**：

```
现在的装配（context.assemble）
  messages = [
    {system: A + B + C},        ← C 里塞了「刚才 6 轮」和本轮的话
    {user:   本轮的话},          ← 又说了一遍
  ]
```

- C 段每轮都变，而它在 system 里 → **prefix 每轮都断**；
- B 段里有「记下 N 件事」，抽取一跑就变 → 连 B 都在动；
- 本轮的话出现两次 → 白花钱。

而官方例一讲得很清楚：第二轮 = 第一轮 + 追加，就能命中。
**能命中的形状只有一种：前缀逐字不变，可变的东西全在末尾。**

## 3. 于是「60%/80%」要换成这几个量

### 3.1 预算 `P` 不是 1M

1M 是能力上限，不是我们的预算。按 `daily=0.667 元/天`、150 轮/天算：

| 每轮 prompt | 全命中/天 | 全未命中/天 |
|---|---|---|
| 4K | 0.012 元 | 0.60 元 |
| 8K | 0.024 元 | 1.20 元 |
| 16K | 0.048 元 | 2.40 元 |
| 64K | 0.19 元 | 9.6 元 |

（flash 空闲价：命中 0.02、未命中 1 元/M）

**结论**：命中时 16K 才 0.05 元/天，可以随便给；未命中时 8K 就已经超预算。
所以 `P` 不该按「省 token」定，而该按**最坏情况可承受**定：`P = 12K`。

超过 `P` 才叫「长」，60% = 7.2K 开始整理，80% = 9.6K 强制。

### 3.2 真正该盯的控制变量是**命中率**，不是 token 数

token 数是「我还有多少余量」，命中率是「我有没有在赔钱」。后者掉下去要立刻反应：

```
最近 20 次调用命中率 < 50%   → 立刻整理（换新窗口），不等 60%
同一窗口、前缀没动、却连续 2 次 0 命中 → 判定缓存过期，换新窗口
```

**最后这条就是你说的「超过缓存时间」，只是改成用证据判，而不是用假设判。**

### 3.3 闲时整理：用节律预测，但要有下限

`预计空闲 > 预计整理时间 × 1.5` 才动手（1.5 是余量：预测本身有误差，
整理到一半他回来了，比不整理更糟——那时候窗口已经换过一次）。

而且整理不是「随时可打断」的：它要先**冻结当前窗口**、写新事件、再开新窗口。
所以「预计空闲」要用下界估计（P10 而不是均值）。

### 3.4 80% 强制时为什么要告诉她

因为强制整理会**让她刚才的状态消失**（窗口换了，前缀没了）。
如果离上次对话很近，她正处在对话中——这时候静悄悄地换掉，
下一条回复就会显得「接不上」。

所以：**强制整理时，她在回复里先说一句**（一句，不长），
整理完继续。用户看得见「断了」，就不会误以为是她的问题。

## 4. 整理不是「丢」，是「写下来」

这是和普通聊天机器人最重要的一条区别：

```
关掉窗口  =  把窗口里的对话抽成事实 → events(kind='consolidate') → 图上若干节点
             然后开新窗口，A/B 段按新的图重写
```

- 整理**本身是事件**：可重放、可追溯、可审计（§3.1）；
- 整理后的记忆**能被她自己检索到**（走同一条 recall 路径）；
- 内容对用户不可见（你的规则），仪表盘只看元数据：窗口长度、命中率、整理次数。

## 5. 落到代码上（分两步）

**第一步（这一轮就能验）**：改装配形状。

```
messages = [
  {system: A + B},                      ← 一天/一小时一变，其余逐字不变
  {user: u1}, {assistant: a1}, ...      ← 追加，永不重写
  {user: recalled + quota + 本轮的话},   ← 所有易变的东西都在最后
]
```

预期：第二、三轮开始出现非零 `prompt_cache_hit_tokens`。这是可判定的——
**要么命中，要么文档里那套说法对我们不成立**，两种结果都有用。

**第二步**：`ctx_windows` 表（窗口开始/长度/命中率/关闭原因）+ 三个触发条件 +
闲时整理挂到 `rhythm` 的预测上。

## 6. 还没定的

- `P=12K` 是拍的，要等真实命中率出来再校；
- 「整理耗时」要先有样本（第一次整理记时间，之后用中位数）；
- 如果实测发现**追加式的长对话命中率依然很低**，那 §6 的成本模型要整个重算——
  这不是「优化」，是「这个系统能不能用」的问题。
