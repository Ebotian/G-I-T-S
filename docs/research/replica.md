# 可恢复的单向副本

> 里程碑：**源 → 副本**，拉取式、可断点续传、重复拉取不产生重复、删除能传过去、副本能独立重放出等价投影。
>
> 这是那个一直没被验证过的架构承诺。现在它有两份独立的 SQLite 库和 9 个测试撑着。

## 1. 三条语义

**（1）游标只在应用成功之后推进。**

中途崩了就从旧游标重来。重来是安全的，因为导入按 `(source, ext_id)` 幂等。这条意味着：**宁可重复应用，不可提前推进**。

**（2）游标按流分别记，不是一个大游标。**

拉取顺序是 `redactions → observability → model_calls → events`。顺序有意义——删掉的东西不该在"还没删"的事件之后才被处理。而删除流落后不会拖住事件流（有测试）。

**（3）投影不传，副本自己重放。**

于是"每天同步一次"等于"每天做一次免费的重放回归测试"（DESIGN §15.8）。`gits verify` 就是把这句话变成命令。

## 2. 用法

```bash
gits --db /tmp/src.db say "会议又超时了"
gits --db /tmp/rep.db sync --src /tmp/src.db
gits --db /tmp/rep.db verify --src /tmp/src.db
```

```
replica: 无新增 · 游标 {'events': 3, 'model_calls': 3} · 落后 0 分钟
✅ 一致
```

## 3. verify 到底在比什么

它**先重放**，再比投影。所以：

| 场景 | 结果 | 为什么 |
|---|---|---|
| 故意删掉副本的 `node_content` | **一致** | 投影是派生物，重放会把它修好——那不是数据丢失 |
| 副本少了一条 `events` | **不一致** | 日志集缺了，重放也补不回来 |
| 副本缺模型结果 | **不一致**（重放直接抛错） | 恢复重放不允许重新调模型 |

第二、三种才是真问题。第一条我一开始写成了"不一致"，错了——**verify 验的是日志集，不是那几张可以被重建的表。**

比较时用 `canonical(stable=True)`，丢掉自增 id：两份库按各自的插入顺序生成自增 id，必然不同；比较语义时不该被它们干扰。

## 4. 两个刻意的限制

**单向上传不做。** 副本只读。工作机产生的麦克风事件要回传，那是**双向**的事，要等身份、租约、冲突处理都定稿（DESIGN §17.8.2）。

**一次拉取有上界**（`limit_rows=500`）。副本可能睡了一周才醒，一次灌十万行会把内存和事务撑爆。分多轮拉完是调用方的事——`gits sync` 里就是一个循环，直到没有新增。

## 5. 还没做的

- **上传**（副本 → 源）：需要双向游标和 echo 合并真正接上（§15.8.5 有设计，没实现）
- **租约校验**：`roles` 表存在，但"写之前校验 epoch"还没接
- **真实的两台机器**：目前只在同机两个文件上验证过；跨机还要加传输层（HTTP 长轮询，§15.4 的设计还没落地）
