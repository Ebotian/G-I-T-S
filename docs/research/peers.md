# 三个实例：差异的物质基础（机制设计，不含内容）

> 前提：三个实例同代码、同模型、同 prompt 骨架、共享 `world`，只有主个体有对外通道。
> 那么「为什么它们会不一样」必须有一个**物质**答案，不能靠自我描述写得不一来实现。
>
> 本文只定机制：接口形状、预算、隔离、怎么判断差异是真的。

## 1. 一句话

**差异来自各自在做什么，不来自各自是谁。**

同一个人给两段人生会变成两个人；给两段自我描述只会变成两个演员。
所以 peer 的接口不是「feed（喂内容）」而是「job（派活）」。

理由很具体：**阅读没有反馈，任务有**。反馈（做成了/做砸了/没人用）才是经历。
没有反馈的经历写不出观点，只能写出摘要——而摘要工厂是最贵的空转。

## 2. 接口形状：job，不是 feed

```
world 事件 / 订阅源  →  任务队列  →  某个实例领取  →  产物进 world
                                                            ↓
                                        她或他用到了 / 没用  ←──┘
                                                ↓
                                         这是那个实例的经历
```

这条链路每个箭头都有已有的落点：

| 环节 | 现有件 |
|---|---|
| 任务 | `sched.Task`（已有 kind/代价/截止） |
| 领取 | `sched.place()` + `eligibility`（节点=实例） |
| 产物 | `events`（source=实例名）+ 一个节点 |
| 用到/没用 | `outcomes`（已经为回复建的） |

也就是说：**peer 接入不需要新概念，只需要把 `sched` 的三硬约束真正跑起来。**

## 3. 三种差异，按可信度排序

| 方式 | 差异来自 | 成本 | 我的判断 |
|---|---|---|---|
| **各自的活** | 做了什么、结果如何 | 低（都是本地活） | ✅ 主路 |
| 各自的关注权重 | 同一批事先看哪一面 | 零 | ✅ 辅路，但**必须有初始不对称** |
| 各自读不同的源 | 输入不同 | 中（抓取/解析） | ⚠️ 只作为任务的一种输入，不单独做 |
| 互相聊天 | 对方的输出 | 高 O(n²) | ❌ 不做 |

**为什么不做互相聊天**：没有反馈、没有产物、成本随人数平方增长，
而且它有一个很隐蔽的失败模式——**它们会越来越像**。
因为彼此的输入就是对方的输出，模型会把对方的措辞学回来，几轮之后三个人说一样的话。

## 4. 趋同是默认结果，不是意外

这一条值得单独写，因为它决定了很多取舍。

三个实例共享 `world`、用同一个模型、读同一批事件的投影。**它们天然会趋同。**
让它们不同的每一件事，都是我们主动加进去的，而且必须是结构性的：

- **任务类型不同**：一个整理索引、一个盯一个源、一个做校对。不同类的活产生**不可比**的产物，
  所以不会互相模仿。
- **互读有代价**：读别人的产物要花额度。免费互读就等于强制合流。
- **各自的下游不同**：只有主个体的产物会进微信被评价；peer 的产物被用到的方式要另外设计，
  否则 peer 永远得不到反馈，也就永远学不到东西。

> 如果一年后它们说话变得很像，原因不会是模型，而是我们没有把上面三条守住。

## 5. 预算：主个体优先，peer 只做便宜活

三个实例共享 `daily ≈ 0.667 元/天`（§18）。所以 peer 的活必须满足：

```
peer 的活 = 检索 / 索引 / 整理 / 校对   ← 本地，零或极低 token
          ≠ 长文生成                  ← 那是主个体的活，因为她的产出有人读
```

分配规则：**主个体先扣，剩余的才是 peer 的**。理由是她的产物有下游（微信），
peer 的产物暂时没有——没有下游的生成是纯支出。

这也和既有的机器分层一致：ghost 120MB 只跑 numpy，statsmodels/onnx 在 dream 层。
peer 的活应该落在 ghost 那一层的能力里，需要重算的时候才进 dream。

## 6. 隔离：现在是约定，不是保证

`scope` 门已经装上了（`recall` 强制要 actor）。但要诚实写在设计里：

```
三个实例共用一个 SQLite → 任何能打开库的人都能看见全部
```

所以现在的私有域是**逻辑隔离**，防的是「代码写错了互相读」，
防不了「有人打开 db 文件」。P0 单用户单机，这样够；但要写在文档里，别写着写着当成真的。

什么时候必须升级到物理隔离：当 peer 开始摄入外部内容（可能有别人的隐私或版权），
或者当用户要求「这个不让她知道」而这句话必须真的成立时。

## 7. 验收：怎么知道差异是真的

不给指标的话，「三个视角」会变成一句自我安慰。三个可测量的数：

| 指标 | 定义 | 及格线 |
|---|---|---|
| 召回交集率 | 同一个 world 事件，三个实例 recall 结果的交集 / 并集 | < 60% |
| 产物互补性 | 同一件 world 事件，三者产物能否被拼成一个更完整的结论 | 人工看 |
| 可解释性 | 每个实例对同一事件的看法，能否追到**它自己的**经历 | 100% |

第三条最重要：如果一个 peer 对某件事有看法，但它的图里找不到依据，
那这个看法就是编的——和人格更新里「挂不上 event_id 就整次作废」是同一条规矩。

## 8. 第一个月只做一件事

```
给三个实例各派一件不同**类型**的活，跑一个月，然后量第 7 节那三个数。
```

不做的事，明确写下来：

- 不做实例之间自由对话
- 不做 peer 的人格更新（没有通道就没有经历，夜里更新会从空气里写字——`persona.update` 已经会拒绝）
- 不做 peer 的对外通道
- 不给 peer 独立的初始人格（起点相同，差异由任务产生）

## 9. 还没答案的两个问题

**① peer 的产物谁用？** 主个体可以用（进她的 C 段），用户看不见（内容不可见规则）。
但如果从来没被用，peer 就永远得不到 `outcomes`，也就永远学不到东西——只是三个人在自转。
这一条没解决，上面所有设计都还只是「让它们看起来不一样」。

**② 三件不同**类型**的活**是什么？这个必须从真实的、对主个体有用的需求里长出来，
不能为了凑差异而发明。现在能想到的候选：

```
整理索引    把近期的 world 事件做成可按主题翻的东西
盯一个源    某个只读来源（技术/新闻/论文），产出摘要+citation
校对        在她要说话之前，检查有没有和已有记忆矛盾的地方
```

三个候选里，第三个和主个体是强耦合的（她的每个回复都过一遍），
所以它天然有下游、有反馈。**如果只能先做一个，做第三个。**
