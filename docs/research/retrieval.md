# 检索：地板价、两个 bug，以及「没有向量提供商」之后怎么办

## 0. 三句话结论

1. **裸问**（「上次那个跟你较劲的事」）的字面召回是 **0.00**——不是效果差，是这条路不通；
2. 但**补上对话上下文之后**，字面召回 @10 到 **0.67–0.75**，**找对实体 0.88–0.92**；
3. 所以 **embedding 不是必需的，是补集**：它负责上下文缺失的那部分，以及
   `potion-multilingual-128M` / `bge-small-zh` 这类模型**放不进 ECS 的 120 MB 预算**。

## 1. 为什么先做词面

因为要给它一个可比较的地板。没有地板，「上了向量之后 recall 从 0 到 0.6」
和「从 0.5 到 0.6」是两件完全不同的事，而后者根本不足以证明向量值得。

## 2. 分词：二元组，不用 jieba

| 方案 | 代价 |
|---|---|
| jieba | 默认词典常驻 **~50 MB RSS**，而 ghost 的依赖预算只有 120 MB |
| **字符二元组** | 索引大一点；无词典、无 OOV、内存零 |

```
tokenize('上次那个跟你较劲的事') → 上次 次那 那个 个跟 跟你 你较 较劲 劲的 的事
tokenize('物07 状态：卡住了')     → 物 07 状态 卡住 住了
```

## 3. 地板价（裸问）

180 天 × 3 个种子，间接提问（不说实体名）：

```
seed=  7  recall@1 0.00 · @5 0.00 · @10 0.00 · 对照命中 0.82
seed= 11  recall@1 0.00 · @5 0.00 · @10 0.00 · 对照命中 0.95
seed= 23  recall@1 0.00 · @5 0.00 · @10 0.00 · 对照命中 0.93
```

**对照那一列是关键**：用事实自己的字面去搜能中 0.82–0.95，所以 0.00 不是索引坏了。

## 4. 上下文扩展：不需要任何提供商

给每条查询补上前两轮聊过的内容（模拟真实对话），再走纯字面检索：

```
                 裸问 @1/@5      带上下文 @1/@5/@10   找对实体   对照
seed=  7         0.00/0.00       0.09/0.31/0.67        0.88     0.82
seed= 11         0.00/0.00       0.10/0.43/0.75        0.92     0.95
seed= 23         0.00/0.00       0.10/0.46/0.71        0.91     0.93
```

**指代是靠上下文解析的，不是靠记忆库。**「上次那个跟你较劲的事」之所以说得通，
是因为上一句还在聊它。

注意 @1 只有 0.09–0.10：同一实体的多条事实字面完全一样，差的是
「是哪一条」，不是「是谁」。所以要分开两个指标：**找对实体** vs **找对哪一条**。

## 5. embedding 提供商：都查过，都不行

| 方案 | 规模 | 能否进 ghost（120 MB） |
|---|---|---|
| `minishlab/potion-multilingual-128M` | Model2Vec 静态向量，bge-m3 蒸馏，256 维，101 语言 | fp32 ≈512 MB ✗ |
| `bge-small-zh-v1.5` | 512 维，≈40M 参数，≈80 MB RSS | ✗（ghost 已用 30 MB） |
| `bge-m3` | 1024 维 | 只可能在工作机上 |
| DeepSeek API | — | **没有 embedding 接口**（VERIFIED §3） |

这是硬件事实，不是选型问题。于是只剩三条路：

**A. 工作机算，向量随作业回传。** 12 核 / 30 GB / 6 GB 显存跑 bge-m3 毫无压力。
卡点在**查询也要向量化**，而工作机 18:00 之后不一定在——恰好也是他不在电脑前的时候。

**B. 上下文扩展。** 见 §4，零成本，已经验证。

**C. LLM 查询扩展。** 用已有的 DeepSeek 把间接说法改写成关键词（`卡住 报错 编译器`）
再走字面检索。一次小调用，几十 token。本质上是在补同一块信息。

## 6. 两个写代码时抓到的 bug

**① `bm25_to_sim` 方向写反了。**

```python
return 1/(1+abs(rank))     # ← bm25 越负越好，这个映射让匹配越好的分越低
```

不报错，只是把结果全排反，而且看起来能跑。对照命中率从 0 变成 0.82 才暴露。

**② 向量如果只做重排钩子，就永远救不回词面漏掉的节点。**

```python
sim = max(fts_sim, vec_of(node_id))        # 错的
merged = fts_candidates | vec_candidates   # 对的
```

「间接提问」恰恰全是词面一个都没召回的情况。有测试钉着这条。

## 7. 打分公式

```
score = 0.55·sim + 0.25·r + 0.10·energy + 0.05·centrality + 0.05·recency
```

刻意保持线性：可解释、可消融。**它不是概率**，只用来排序。
权重是初始值，等有了真实查询再调——现在调等于拟合噪声。

## 8. 立即可做（不依赖任何提供商）

1. **上下文扩展接进检索**：`search` 多传一段 context 即可，已经能拿到 0.67–0.75；
2. **结构化排序**：同一实体 + 同一谓词下按 `r`（FSRS 算，不花钱）排，
   这能把 @1 从 0.10 拉起来——那才是「是哪一条」的正确解法；
3. **LLM 查询扩展**作为 C 选项，等 B 的成绩出来再决定要不要加。

向量留在 `candidates_of` 钩子上。哪天真有提供商、或者工作机闲置算力可用，
接上去，同一个 `eval_search` 立刻能量出它补回来多少。
