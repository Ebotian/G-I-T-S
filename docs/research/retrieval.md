# 检索：先量地板价，再谈向量

> 结论：**间接提问的词面召回是 0.00**。
> 这不是「效果一般」，是「这条路根本不通」——所以 embedding 不是可选优化，是必需品。

## 1. 为什么先做词面

因为要给它一个可比较的地板。没有地板，「上了向量之后 recall 从 0 到 0.6」
和「从 0.5 到 0.6」是两件完全不同的事，而后者根本不足以证明向量值得。

## 2. 分词：二元组，不用 jieba

| 方案 | 代价 |
|---|---|
| jieba | 默认词典常驻 **~50 MB RSS**，而 ghost 的依赖预算只有 120 MB |
| **字符二元组** | 索引大一点；无词典、无 OOV、内存零 |

jieba 还会漏人名、新词、代码片段——而这些东西恰好是「他会提起的事」。
二元组全都覆盖。

```
tokenize('上次那个跟你较劲的事') → 上次 次那 那个 个跟 跟你 你较 较劲 劲的 的事
tokenize('物07 状态：卡住了')     → 物 07 状态 卡住 住了
```

## 3. 结果：地板是零

180 天 × 3 个种子，间接提问（不说实体名）：

```
seed=  7  查询 102 条 · recall@1 0.00 · @5 0.00 · @10 0.00 · 对照命中 0.82
seed= 11  查询 106 条 · recall@1 0.00 · @5 0.00 · @10 0.00 · 对照命中 0.95
seed= 23  查询 107 条 · recall@1 0.00 · @5 0.00 · @10 0.00 · 对照命中 0.93
```

**对照那一列是这个实验的关键**：用事实自己的字面去搜，命中 0.82–0.95。
所以 0.00 不是因为索引坏了，而是因为间接提问和事实之间**没有任何字面重叠**。

（对照没到 1.00 也有意义：很多事实共用同一套谓词和取值，字面完全一样。
这正好说明**实体身份**本身也是信息，字面检索连它都区分不了。）

## 4. 向量必须是一条召回通道，不是重排钩子

写代码时的一个教训：

```python
# 错的：只给已有候选重排
sim = max(fts_sim, vec_of(node_id))
```

这样词面没召回的节点**永远不会出现**，向量再准也救不回来。
而「间接提问」的情况就是「词面一个都没召回」。

正确的是并集：

```python
merged = fts_candidates | vec_candidates     # 两条通道各自召回，再合并取高
```

有测试钉着这一条（`test_向量是另一条召回通道_不是重排钩子`）。

## 5. 还有一个方向写反的 bug

`bm25_to_sim` 我第一版写成 `1/(1+|rank|)`——**bm25 越负越好，所以这个映射
让匹配越好的分数越低**。它不报错，只是把结果全排反，而且看起来能跑。

对照命中率从 0 变成 0.82 才让它暴露。

```python
def bm25_to_sim(rank):
    a = abs(rank)          # 越负 → a 越大 → sim 越高
    return a / (1 + a)
```

## 6. 打分公式

```
score = 0.55·sim + 0.25·r + 0.10·energy + 0.05·centrality + 0.05·recency
```

刻意保持线性：可解释、可消融、调参不玄学。**它不是概率**，只用来排序。

权重是初始值，等有了向量召回和真实查询之后再调——现在调等于拟合噪声。
