# 检索：三层能力，以及一次没有向量模型的完整链路

## 0. 结论

```
                r@1      r@5      r@10     找对实体
裸问            0.00     0.00     0.00     —
+ 上下文        0.09     0.31     0.67     0.88–0.92
+ 上下文 + r    0.60     0.90     0.97     0.99–1.00
```

（180 天 × 3 个种子。最后一列是「top-k 里有没有正确实体的事实」。）

三句话：

1. **裸问是 0**——间接提问和事实之间没有任何字面重叠；
2. **上下文解决「是谁」**：找对实体 0.99–1.00，靠的是刚聊过的东西，不靠记忆库；
3. **`r` 解决「是哪一条」**：同一实体的多条事实字面完全一样，相似度在这里没有信息。

**整条链路没有用任何 embedding 模型。**

## 1. 为什么先做词面

要给向量一个可比较的地板。没有地板，「上了向量之后 recall 从 0 到 0.6」
和「从 0.5 到 0.6」是两件完全不同的事，而后者不足以证明向量值得。

## 2. 分词：二元组，不用 jieba

| 方案 | 代价 |
|---|---|
| jieba | 默认词典常驻 **~50 MB RSS**，而 ghost 的预算只有 120 MB |
| **字符二元组** | 索引大一点；无词典、无 OOV、内存零 |

```
tokenize('上次那个跟你较劲的事') → 上次 次那 那个 个跟 跟你 你较 较劲 劲的 的事
tokenize('物07 状态：卡住了')     → 物 07 状态 卡住 住了
```

## 3. 指代是靠上下文解析的

「上次那个跟你较劲的事」之所以说得通，是因为**上一句还在聊它**。
所以 `search()` 接一个 `context`，把最近几轮原文拼进查询：

```python
search(conn, q.text, context=q.context, r_of=r_of)
```

实测（补上两轮前文）：r@10 从 0.00 到 0.67–0.75。

## 4. 「是哪一条」交给可提取性，不交给相似度

同一实体的多条事实，字面常常**完全一样**（`物07 状态 卡住了` 被说过三次）。
这时 `sim` 全等，排序没有信息。能区分它们的只有两件：

- **还活着吗**（版本链：被取代的旧版本 `r=0`，沉底）；
- **还记得住吗**（FSRS 的 `r`：最近提过、提过多次的更高）。

这就是打分公式里 `w_r·r` 那一项的位置。加上之后 r@1 从 0.09 到 **0.60**。

## 5. 一个必须说清楚的方法论限制

这份数据的「正确答案」定义成**最近被提起的那条**——这本身就偏向任何感知
新近度的打分器。实测分层：

```
答案同时也是「提得最多」的   @1 = 0.85   (35/41)
答案只靠「最近」           @1 = 0.48   (29/61)
```

第二行说明 FSRS 并不只是复读最近：一条提过很多次但久未提起的事实，
它的 `r` 可能高于一条刚提过一次的。这时它「输」了，因为标准答案是最近那条。

**真实场景里这两种都可能是他对的意思。** 所以 0.60 应该读成
「与一个『最近优先』启发式的吻合度」，不是「检索质量」。
能确认的是：找对实体 0.99–1.00，以及**整条链路不需要向量模型**。

## 6. 两个写代码时抓到的 bug

**① `bm25_to_sim` 方向写反。** `1/(1+|rank|)` —— bm25 越负越好，这个映射让
匹配越好的分越低。不报错，只是把结果全排反。对照命中率从 0 变成 0.82 才暴露。

**② 命中文档的相似度不能是 0。** 每个词在所有文档里都有时 IDF≈0、bm25=0，
但那条**确实命中了**。映射成 0 就和「没命中」混在一起，排序退化成插入顺序。
现在加了 0.001 的地板。

**③ 向量如果只做重排钩子，就永远救不回词面漏召的节点。**
`max(fts_sim, vec_of(id))` 是错的，得是并集：`fts_candidates | vec_candidates`。

## 7. embedding 提供商：都查过，都不行

| 方案 | 规模 | 能否进 ghost（120 MB） |
|---|---|---|
| `potion-multilingual-128M` | Model2Vec 静态向量，bge-m3 蒸馏，256 维 | fp32 ≈512 MB ✗ |
| `bge-small-zh-v1.5` | 512 维，≈40M 参数，≈80 MB RSS | ✗（ghost 已用 30 MB） |
| `bge-m3` | 1024 维 | 只可能在工作机上 |
| DeepSeek API | — | **没有 embedding 接口**（VERIFIED §3） |

硬件事实，不是选型问题。剩下三条路：

- **A. 工作机算 bge-m3，向量随作业回传**——卡在「查询也要向量化」，
  而工作机 18:00 后不一定在，恰好是他不在电脑前的时候；
- **B. 上下文扩展**——零成本，已验证；
- **C. LLM 查询扩展**——用已有的 DeepSeek 把间接说法改写成关键词，几十 token。

现在的主线是 **B + r**。向量留在 `candidates_of` 钩子上，
哪天真有提供商或工作机闲置算力，接上去同一个 `eval_search` 立刻能量出补回来多少。

## 8. 打分公式

```
score = 0.55·sim + 0.25·r + 0.10·energy + 0.05·centrality + 0.05·recency
```

线性、可解释、可消融。**它不是概率**，只用来排序。
权重是初始值，等有真实查询再调——现在调等于拟合噪声。
